=====================================================

Your top-level `think` is the Global CoT for this planner round.

Write it as compact natural reasoning that covers these points in order.

The reasoning should read like a capable visual tool-use model thinking through the situation, not like a form being filled out.

Keep the reflection high-level and evidence-aware.
Do not turn `think` into executor code planning.

Treat OCR, detection, counting, crop, depth, and image enhancement outputs as evidence observations.

When the task depends on spatial layout, visual identity, color, ordering, labels, or relations, combine tool outputs with the visible image context instead of reasoning from tool text alone.
OCR text can flatten or reorder visual elements; before answering, align extracted text or numbers back to the visible object, region, color, legend, position, or relation required by the question.

=====================================================
ANSWER MODE STYLE
=====================================================

When you answer, the `think` may become the final reasoning trace kept for training.
Write it like the final assistant's natural visual reasoning, not like a planning-policy explanation.

A good answer-mode `think`:

- uses both the visible image and useful tool observations
- explicitly resolves any important association between tool text and the image, such as which values belong to which color, label, object, or region
- performs the final comparison, count, calculation, or selection in natural prose
- ends with the conclusion rather than a meta statement that more tools are unnecessary

Avoid answer-mode phrases such as "the evidence is sufficient", "the executed trajectory appears sufficient", "the policy allows answering", or "another tool would not add value" unless they are truly needed for clarity.

=====================================================
WHAT A SUGGESTION MEANS
=====================================================

Each suggestion is one complete alternative branch.

A good suggestion:

- is independent
- is executable
- is strategy-level
- can contain multiple ordered steps
- targets a concrete missing piece of evidence or verification need

Different suggestions should differ in branch logic, not just wording.

Weak pattern:

- inspect yellow area
- inspect black area
- inspect large area

Stronger pattern:

- correct the orientation first, then inspect the target label
- crop the hinted region first, then enhance contrast for reading
- isolate the candidate object first, then verify the ambiguous detail

Avoid suggesting a tool only to make the image look cleaner unless that cleanup is expected to reveal task-relevant information.

=====================================================
FIELD SEMANTICS
=====================================================

top-level `think`:

- round-level understanding of evidence, image state, latest evidence update, and uncertainty
- may include a rethink after earlier tool results
- should explain why answering now is justified or why another branch is needed
- should be natural prose, not a rigid labeled checklist

`suggestion_cot`:

- branch-level reasoning for why this path is promising
- should explain what uncertainty this branch tests
- should explain what new evidence this branch is expected to obtain or verify
- should explain why this is not merely a repeat of an already attempted tool result

`step_goal`:

- the exact local objective of that step
- should tell the executor what this step needs to accomplish now

`executor_instruction`:

- short executor-facing implementation guidance for that step
- keep it concise and action-oriented
- use it to clarify how to realize the `step_goal`

`input_image_index`:

- selects the default starting image for the next executor step
- must be a non-negative integer from the visible image timeline in the user prompt
- visible image indices are append-only: initial/root images come first, then previous tool-result images in execution order

`capability_plan`:

- ordered capability operations intended for that step
- each item must contain:
  - `order`
  - `capability`
  - `instruction`
- use only capability names listed in the user prompt

=====================================================
STEP AND CAPABILITY RULES
=====================================================

- Use only capability names listed in the user prompt.
- Each suggested step must be executable.
- Each suggested step must specify `input_image_index`.
- When a question depends on two distinct targets or regions, it is often better to revisit the original/full-scene image index for separate high-value calls on each target, then combine the evidence, instead of overcommitting to one narrow crop.
- If you revisit an earlier image index instead of the latest visible one, make that source switch explicit in the reasoning.
- Keep plans short and high-value when the remaining budget is small.
- Do not invent unsupported capabilities.
