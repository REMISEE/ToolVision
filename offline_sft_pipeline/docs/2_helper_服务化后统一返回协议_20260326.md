# 2 Helper 服务化后统一返回协议

日期：2026-03-26  
状态：v0.1 对齐稿  
目的：在未来 OCR、GroundSAM、depth、count 等能力逐步独立服务化后，保持 helper 接口和上层 pipeline 稳定。

---

## 1. 先讲结论

未来即使底层模型全部改成独立 HTTP/gRPC 服务，也不建议改 helper 名字和 helper 的上层协议。

应该稳定保留：

- `_call_ocr_assist`
- `_call_ground_box`
- `_call_sam_mask`
- `_call_dino_crop`
- `_call_blur_bg`

未来新增：

- `_call_depth_assist`
- `_call_count_assist`

是否这样命名后面可再定，但核心原则不变：

> helper 名和 helper 返回协议对上层保持稳定，底层模型服务可以自由更换。

---

## 2. 统一协议要分两层理解

这里最容易混淆的是：

- “远端模型服务返回什么”
- “helper 在安全执行环境里返回什么”

这两层不要混为一谈。

### 2.1 服务层返回

这是 HTTP / gRPC 服务给 adapter 的返回。

### 2.2 helper 层返回

这是 `_call_ocr_assist()` 这类 helper 在代码执行环境里返回给 executor 代码的对象。

真正对 pipeline 最重要、最应该稳定的是第二层。

---

## 3. helper 层统一返回协议

建议未来所有 helper 在 `CodeImageTool` 安全执行环境里都统一成：

```python
{
    "image": PIL.Image | None,
    "images": list[PIL.Image],
    "text": str,
    "meta": dict
}
```

这和当前已经在用的返回形状保持一致。

### 字段含义

#### `image`

- 主返回图
- 通常等于 `images[0]`
- 如果没有图像返回，可以为 `None`

#### `images`

- 本次 helper 返回的全部图像
- 允许多图，不强制拼图

#### `text`

- 本次 helper 返回的文本信息
- 应该尽量是 tool 的真实文本返回
- 不要默认写成人工摘要

典型内容包括：

- OCR 文本
- OCR tokens
- count 的数值输出
- depth 的排序或比较结果
- 结构化工具返回里的原始文本字段

不建议默认把“步骤摘要式说明”塞进 `text`。

如果需要额外的摘要、解释或对后续 step 的提示，建议写进 `meta`，例如：

- `meta.semantic_note`
- `meta.summary_text`
- `meta.pipeline_hint`

#### `meta`

- 结构化补充信息
- 这是最关键的字段之一

建议里面至少允许保存：

- `model`
- `operation`
- `boxes`
- `masks`
- `crop_boxes`
- `scores`
- `raw_text`
- `service_name`
- `service_latency_ms`

---

## 4. 为什么 `meta` 必须保留

因为未来服务化以后：

- 真正丰富的信息往往在结构化返回里
- 不能只靠 `ToolResponse.text`

尤其 offline pipeline 还需要：

- judge
- replay
- exporter
- 错误定位

所以：

- `text` 给模型和上层真实消费
- `meta` 给系统和后处理

---

## 5. 远端服务层推荐的标准化返回

虽然上层真正稳定的是 helper 协议，但服务层也建议尽量统一。

推荐远端服务返回的 JSON 形状为：

```json
{
  "success": true,
  "text": "138 140 142",
  "meta": {
    "model": "grounded_sam_v_next",
    "operation": "ocr",
    "summary_text": "ocr tokens for the cropped region"
  },
  "images": [
    {
      "media_type": "image/png",
      "encoding": "base64",
      "data": "<base64>"
    }
  ],
  "error": null
}
```

其中：

- `success`：服务调用是否成功
- `text`：真实 tool 文本返回
- `meta`：结构化信息
- `images`：图像数组
- `error`：失败时的错误信息

然后由 adapter 把它转成 helper 层返回：

```python
{
    "image": decoded_images[0] if decoded_images else None,
    "images": decoded_images,
    "text": text,
    "meta": meta,
}
```

## 6. 错误协议建议

如果远端服务失败，建议统一返回：

```json
{
  "success": false,
  "text": "",
  "meta": {},
  "images": [],
  "error": {
    "type": "service_timeout",
    "message": "request timed out after 30s"
  }
}
```

然后 helper 层可以：

1. 直接抛异常  
或
2. 返回空图像并把错误写进 `meta`

更推荐第一种：

- service 失败直接让当前 step 失败
- 再由 runtime wrapper 统一写入 `runtime_result.error`

这样错误链路最清楚。

---

## 7. 为什么 helper 名字不要跟模型名绑死

因为未来你已经明确会发生：

- PP-OCR -> PP-OCRv5
- GroundSAM 重新封装
- 后面新模型继续替换

如果 helper 名直接叫模型名，训练数据和 prompt 会被底层实现绑死。

所以建议：

- helper 名保持能力语义或稳定别名
- 底层具体服务放进 `meta.model` 或 adapter 配置里

当前短期可以保留现有名字，是因为它们已经形成使用习惯。

但长期建议内部再区分：

- helper 稳定名
- service/model 具体实现名

## 8. 和 `runtime_result_schema` 的关系

未来 runtime 里真正要写进：

- [executor_runtime_result_schema.json](/data/home/suchenghao/ToolVision/offline_sft_pipeline/schemas/executor_runtime_result_schema.json)

的关键字段就是：

- `images`
- `text`
- `meta`
- `observed_helper_calls`

也就是说，helper 服务化以后，这份统一协议就是 runtime result 的上游来源。

---

## 9. 当前建议冻结的协议

建议现在就冻结：

### helper 层稳定协议

```python
{
    "image": PIL.Image | None,
    "images": list[PIL.Image],
    "text": str,
    "meta": dict
}
```

### 服务层推荐协议

```json
{
  "success": true | false,
  "text": "tool raw text",
  "meta": {...},
  "images": [...],
  "error": null | {...}
}
```

---

## 10. 一句话版本

未来可以把模型服务全部推倒重做，但不要动 helper 协议；上层 pipeline 应该只依赖稳定的 helper 返回结构，而不是依赖具体模型服务的长相。
