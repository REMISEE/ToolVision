# 11 Step 3：Planner / Executor / Judge Client 接口设计

日期：2026-03-29  
状态：设计稿  
目的：定义 Step 3 的最小可实现方案，使 `planner / executor / judge client` 先用 fake backend 跑通，同一套 pipeline 以后可直接切到真实模型 / judge 部署，而不推倒重写。

---

## 1. 一句话结论

Step 3 最合理的实现方式是：

- 直接写真实 `PlannerClient`
- 直接写真实 `ExecutorClient`
- 直接写真实 `JudgeClient`
- 底层只把“模型来源 / judge 评分来源”做成可插拔 backend

当前先接：

- `FakeTextBackend`
- `FakeJudgeBackend`

后面再接：

- `ApiTextBackend`
- `CommitteeJudgeBackend`

这样现在可以：

- 用 fake 数据跑通
- 保持和未来真实系统同一条 parse / validate / store / orchestrator 链
- 不额外发明一套临时 fake-only 架构

---

## 2. 设计原则

### 2.1 CoT 永远放最前

planner 和 executor 的模型返回里，`CoT` 都应该最先出现。

原因：

1. prompt 更自然
2. 强模型更容易按顺序先思考、再给结果
3. parser 规则更清楚

因此：

- planner：先 `<think>`，再 `<answer>` 或 `<suggestions>`
- executor：先 `<think>`，再 `<code>`

### 2.2 模型返回尽量简单

不要让强模型直接生成完整持久化 JSON。

应该让模型只生成它最擅长的那部分：

- `think`
- `answer`
- `suggestions`
- `code`

然后由后端 / client 去做：

- tag 提取
- 结构化拼装
- 字段补齐
- schema 校验

### 2.3 fake backend 不新增原始文本文件

当前不建议额外落：

- `fake_planner_raw.txt`
- `fake_executor_raw.txt`
- `fake_judge_raw.txt`

默认仍然只落正式文件：

- planner -> `planner/round_xxx.json`
- executor -> `steps/step_xxx/executor_cot.md`
- executor -> `steps/step_xxx/executor_code.py`
- runtime -> `steps/step_xxx/runtime_result.json`
- judge -> `judge/*.json`

也就是说：

> fake backend 只是在内存里伪造“模型回答文本”，然后立刻进入和真实系统一致的 parser / validate / store 流程。

### 2.4 judge 和 planner / executor 不必完全同构

judge 这一块后面要走：

- 10 个模型打分
- 聚合求均值

所以 judge 不一定要和 planner / executor 一样走“单次文本生成 + tag 解析”。

更合理的是：

- `JudgeClient` 仍然保留
- 但它依赖的是 `JudgeBackend`
- `JudgeBackend` 内部再去调用多个模型并聚合

这样：

- client 层仍统一
- judge 的复杂性被压到 backend 里

## 3. 代码应该放哪里

当前仓库已经有：

- `offline_sft_pipeline/pipelines/`
- `offline_sft_pipeline/prompts/`

所以 Step 3 不建议再新开一个平行的 `clients/` 目录。

更顺的做法是：

```text
offline_sft_pipeline/
├── pipelines/
│   ├── __init__.py
│   ├── backends.py
│   ├── parsing.py
│   ├── request_models.py
│   ├── planner_client.py
│   ├── executor_client.py
│   ├── judge_client.py
│   └── orchestrator_v01.py
└── prompts/
    ├── planner_system_v01.txt
    ├── planner_user_v01.txt
    ├── executor_system_v01.txt
    ├── executor_user_v01.txt
    ├── judge_system_v01.txt
    └── judge_user_v01.txt
```

职责建议：

- `core/`
  - 放 schema-backed models、store、底层公共对象
- `runtime/`
  - 放 `CodeImageTool` runtime wrapper
- `pipelines/`
  - 放 Step 3 和 Step 4 的流程层代码
- `prompts/`
  - 放 prompt 模板文本

一句话说：

> `core` 是基础设施，`pipelines` 是编排层，`prompts` 是模型交互模板层。

## 4. backend 抽象建议

### 4.1 文本生成 backend

planner 和 executor 统一走文本生成 backend。

建议定义：

```python
@dataclass(slots=True)
class BackendResponse:
    text: str
    raw_payload: dict[str, Any] | None = None
    metadata: dict[str, Any] = field(default_factory=dict)
```

再定义：

```python
class TextGenerationBackend(Protocol):
    def generate(
        self,
        *,
        stage: Literal["planner", "executor"],
        system_prompt: str,
        user_prompt: str,
    ) -> BackendResponse: ...
```

当前直接给两个实现：

1. `FakeTextBackend`
2. `ApiTextBackend`

其中：

- `FakeTextBackend` 当前可用
- `ApiTextBackend` 先留 TODO

### 4.2 judge backend

judge 单独走评分 backend。

建议定义：

```python
@dataclass(slots=True)
class JudgeBackendResult:
    keep_for_frontier: bool
    exportable: bool
    overall_score: float
    answerability_score: float | None = None
    tool_use_quality_score: float | None = None
    trajectory_progress_score: float | None = None
    note: str = ""
    metadata: dict[str, Any] = field(default_factory=dict)
```

再定义：

```python
class JudgeBackend(Protocol):
    def score(self, request: "JudgeClientRequest") -> JudgeBackendResult: ...
```

当前直接给两个实现：

1. `FakeJudgeBackend`
2. `CommitteeJudgeBackend`

其中：

- `FakeJudgeBackend` 当前可用
- `CommitteeJudgeBackend` 先留 TODO

这个 TODO backend 的职责就是：

- 调 10 个 judge model
- 汇总单模型打分
- 取平均 / 聚合
- 返回最终可写 `JudgeRecord` 的分数对象

## 5. 模型返回格式

这里改成最简版本。

### 5.1 planner

planner 只需要 3 个块：

- `<think>`
- `<answer>`
- `<suggestions>`

其中：

- `think` 必须先出现
- `answer` 和 `suggestions` 二选一
- 如果能直接答，就只输出 `<answer>`
- 如果不能直接答，就输出 `<suggestions>`

#### planner 可直接回答时

```text
<think>
The question can be answered from the currently visible crop without more tool use.
</think>
<answer>
The sign says STOP.
</answer>
```

#### planner 需要继续规划时

```text
<think>
We still need to localize the relevant sign and inspect its text.
</think>
<suggestions>
[
  {
    "suggestion_id": "s1",
    "suggestion_cot": "Use grounding and crop to inspect the sign text.",
    "steps": [
      {
        "step_id": "step_a",
        "step_goal": "Locate the candidate sign region.",
        "capability_plan": [
          {
            "order": 1,
            "capability": "ground_box",
            "instruction": "Ground the sign-like object relevant to the question."
          }
        ],
        "executor_instruction": "Write code to ground the relevant sign-like object and keep the crop result for next reasoning."
      }
    ]
  }
]
</suggestions>
```

这里 `suggestions` 里仍然建议放 JSON。

原因：

- 它本身是嵌套结构
- 后端好转成 `PlannerSuggestion` / `PlannerStepSpec`
- 比让模型生成多层 tag 更稳

### 5.2 executor

executor 只需要 2 个块：

- `<think>`
- `<code>`

格式建议为：

```text
<think>
First ground the sign-like target, then crop it and inspect the returned text.
</think>
<code>
box = _call_ground_box("target sign")
crop = _call_dino_crop("target sign", image_obj=box["image"], based_on="box", max_crops=1, padding=8)
print(crop.get("text", ""))
result = crop["image"]
</code>
```

注意：

- 不要要求模型输出 JSON
- 不要要求模型输出 `raw_response_text`
- 不要要求模型输出 `metadata`
- `ExecutorClient` parse 成功后自己补：
  - `raw_response_text = backend_response.text`
  - `metadata = backend_response.metadata`

### 5.3 judge

judge 不建议再设计成：

- `<judge_output>`

也不建议先让模型生成文本，再在 client 里拼评分。

更合理的方式是：

- `JudgeBackend` 内部处理 10 模型打分
- `JudgeClient` 直接拿 `JudgeBackendResult`
- `JudgeClient` 负责补齐 `judge_record_id` 等系统字段

所以 judge 这一侧当前不需要定义文本 tag 协议，只需要定义 backend 接口。

## 6. parser 设计建议

当前 parser 只需要服务 planner 和 executor。

建议做几个最小 helper：

```python
def extract_tag_block(text: str, tag: str) -> str | None:
    ...

def extract_required_tag(text: str, tag: str) -> str:
    ...

def parse_json_text(text: str) -> Any:
    ...
```

使用方式：

- planner：
  - `think = extract_required_tag(text, "think")`
  - `answer = extract_tag_block(text, "answer")`
  - `suggestions_text = extract_tag_block(text, "suggestions")`
- executor：
  - `think = extract_required_tag(text, "think")`
  - `code = extract_required_tag(text, "code")`

planner 的规则建议固定为：

1. 必须有 `<think>`
2. `<answer>` 和 `<suggestions>` 只能出现一个
3. 如果有 `<suggestions>`，其内部必须能 `json.loads`

解析失败时抛统一异常，例如：

```python
class ModelResponseParseError(ValueError):
    ...
```

建议错误里至少带：

- `stage`
- `tag`
- 原始文本前 500 字

## 7. 三个 client 的职责

### 7.1 `PlannerClient`

建议接口：

```python
class PlannerClient:
    def run(self, request: PlannerClientRequest) -> PlannerOutput:
        ...
```

执行流程：

1. 从 `prompts/` 读取 planner system / user prompt 模板
2. 用 `request` 填 prompt
3. 调 `TextGenerationBackend.generate(stage="planner", ...)`
4. parse：
   - `<think>`
   - `<answer>` 或 `<suggestions>`
5. 后端 / client 组装成结构化 draft
6. 补齐：
   - `sample_id`
   - `trajectory_id`
   - `round_idx`
   - `created_at`
7. 生成 `PlannerOutput`
8. `validate_against_schema()`
9. 返回

这里 `can_answer_now` 的判断应直接来自：

- 是否存在 `<answer>`

### 7.2 `ExecutorClient`

建议接口：

```python
class ExecutorClient:
    def run(self, request: ExecutorClientRequest) -> ExecutorStepOutput:
        ...
```

执行流程：

1. 从 `prompts/` 读取 executor system / user prompt 模板
2. 用 `request` 填 prompt
3. 调 `TextGenerationBackend.generate(stage="executor", ...)`
4. parse：
   - `<think>`
   - `<code>`
5. 补齐：
   - `raw_response_text`
   - `metadata`
6. 生成 `ExecutorStepOutput`
7. `validate_against_schema()`
8. 返回

### 7.3 `JudgeClient`

建议接口：

```python
class JudgeClient:
    def run(self, request: JudgeClientRequest) -> JudgeRecord:
        ...
```

执行流程：

1. 把 request 交给 `JudgeBackend.score(...)`
2. 得到 `JudgeBackendResult`
3. 补齐：
   - `judge_record_id`
   - `sample_id`
   - `trajectory_id`
   - `scope_type`
   - `scope_step_idx`
   - `judge_stage`
   - `created_at`
4. 生成 `JudgeRecord`
5. `validate_against_schema()`
6. 返回

换句话说：

> `JudgeClient` 本身不处理 10 模型投票细节，它只处理“拿聚合结果 -> 写成标准记录”。

## 9. fake backend 怎么写才最顺

### 9.1 `FakeTextBackend`

不要让它直接返回：

- `PlannerOutput`
- `ExecutorStepOutput`

正确做法是让它返回和未来真实模型一致的文本回答，例如：

```python
class FakeTextBackend:
    def generate(...):
        if stage == "planner":
            return BackendResponse(text=build_fake_planner_text(...))
        if stage == "executor":
            return BackendResponse(text=build_fake_executor_text(...))
```

这样现在就能验证完整真实链：

- prompt builder
- backend
- parser
- validate
- enrich

### 9.2 `FakeJudgeBackend`

judge fake backend 直接返回：

```python
JudgeBackendResult(...)
```

这样能模拟以后真实的 committee judge 聚合接口。

## 10. 和 store / runtime 的衔接顺序

### 10.1 planner 阶段

`PlannerClient.run(...) -> PlannerOutput`

然后 orchestrator：

1. 选择当前要执行的 suggestion / step
2. 构造 `PendingExecution`
3. `store.register_planner_round(...)`

### 10.2 executor 阶段

`ExecutorClient.run(...) -> ExecutorStepOutput`

然后 orchestrator：

1. `store.write_executor_step_files(...)`
2. 正式落：
   - `executor_cot.md`
   - `executor_code.py`

这里不需要额外 executor raw 文件。

### 10.3 runtime 阶段

runtime wrapper 已经存在。

orchestrator 负责：

1. 构造 `RuntimeStepRequest`
2. 调 runtime wrapper
3. 产出 `runtime_result.json`

### 10.4 step register 阶段

runtime 成功后，orchestrator 再：

1. 生成 assistant message
2. 生成 tool message
3. `store.append_messages(...)`
4. 构造 `StepRecord`
5. `store.register_step_record(...)`

注意：

- `StepRecord` 不由 executor client 返回
- 它是 orchestrator 汇总上下文后的系统记录对象

### 10.5 judge 阶段

`JudgeClient.run(...) -> JudgeRecord`

然后 orchestrator：

1. `store.register_judge_record(...)`
2. 根据分数 / `keep_for_frontier` / `exportable` 决定后续状态

## 11. 最小 orchestrator 应该做什么

如果只追求 v0.1 先跑通，orchestrator 不需要一上来就做完整 branching。

最小版本建议：

1. root trajectory 初始化
2. planner 产出一轮 `PlannerOutput`
3. 只选择 `suggestions[0].steps[0]`
4. executor 生成 `think + code`
5. runtime 执行
6. step register
7. judge
8. 根据 judge 决定：
   - 继续下一轮 planner
   - 或终止 trajectory

这已经能验证：

- models
- store
- runtime
- planner client
- executor client
- judge client
- parser
- end-to-end 主循环

之后再扩到：

- 多 suggestion frontier selection
- child trajectory fork
- committee judge
- exporter

## 12. 现在做到什么程度，才算“pipeline 跑通”

如果下面这些都具备，我认为就可以算：

> v0.1 最小 pipeline 已经跑通

需要满足：

1. root sample 能初始化 trajectory
2. planner client 能产出合法 `PlannerOutput`
3. executor client 能产出合法 `ExecutorStepOutput`
4. runtime 能真实生成 `runtime_result.json`
5. judge client 能产出合法 `JudgeRecord`
6. orchestrator 能把一轮 planner -> executor -> runtime -> judge 串起来
7. trajectory / messages / planner / step / judge 都能正确落盘

这时就已经可以转去做：

- 真实模型调用接入
- judge model 部署
- prompt 打磨
- 解析健壮性增强

但这还不是完整生产版，因为还缺：

- branching / frontier 策略
- child trajectory 调度
- exporter 主循环
- 失败恢复和重试策略

## 14. 一句话版本

> 把 CoT 放在最前，planner 用 `<think> + <answer|suggestions>`，executor 用 `<think> + <code>`，judge 单独走聚合后端；实现代码放进 `pipelines/`，prompt 模板放进 `prompts/`，三 client 加最小 orchestrator 跑通后，就可以开始接真实模型和 judge 部署。
