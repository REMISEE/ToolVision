# 8 v0.1 自动化 Pipeline 实施计划与 Judge 策略

日期：2026-03-29  
状态：v0.1 实施文档  
目的：把当前关于“全量存储 vs 导出”“judge 是否阻塞主循环”“自动化 pipeline 实际运行形态”“下一步最先做什么”这几件事讲清楚，并作为后续实现的直接依据。

---

## 1. 一句话结论

当前最合理的 v0.1 路线是：

1. **所有 trajectory 全量存储**
2. **所有 terminal trajectory 先统一导出**
3. **最终训练集再从导出结果里筛子集**
4. **judge 分成同步控制层和异步分析层**
5. **主循环只被同步 judge 阻塞，不被重 committee 阻塞**

也就是说：

- “全量存储”
- “全量导出 terminal”
- “最终只筛高质量 answered 训练”

这三者并不冲突，而是三层不同语义。

---

## 2. 先澄清：存储、导出、训练不是一回事

这个问题最容易混。

### 2.1 存储层

存储层的原则是：

> 所有 trajectory 都要存下来。

包括：

- `running`
- `answered`
- `pruned`
- `failed`
- `stopped_early`
- `max_step_reached`
- `error`

原因：

1. 便于 resume
2. 便于回放和 debug
3. 便于分析 planner / executor / judge 的真实行为
4. 便于后续做 repair / critique / filtering

### 2.2 导出层

导出层的原则是：

> v0.1 先导出全部 terminal trajectory。

这里的 terminal 指：

- 已经结束
- 不再继续扩展

例如：

- `answered`
- `pruned`
- `failed`
- `stopped_early`
- `max_step_reached`
- `error`

原因不是“这些都要直接拿去训练”，而是：

1. 避免某些 sample 因为没有成功 answered 分支而导空
2. 保留完整分析材料
3. 让后处理筛选规则可以独立演进，不必每改一次筛选逻辑都重跑整套生成 pipeline

### 2.3 训练层

训练层的原则是：

> 最终训练集只是导出层里的一个子集。

最常见的主训练子集是：

- `answered`
- judge 高分
- 与 gold answer 一致

另外还可以有其他用途的数据子集：

- 错误轨迹 -> repair/self-correction 数据
- failed/pruned 轨迹 -> judge/critique 数据
- 低质量 answered -> analysis pool，不直接进入主 SFT

所以：

- **存储** 是全量账本
- **导出** 是统一线性化
- **训练** 是导出之后再筛子集

---

## 3. Judge 不能只有一种

这是当前实现上必须先定清楚的点。

如果 judge 的分数会直接参与：

- 是否继续下一轮 planner
- 是否提前早停
- 是否因为连续两轮分数不变而停掉
- 是否因为分数变低而剪枝

那么这个 judge 就不能是“完全异步回填、对主循环无影响”的后台分析器。

否则会出现：

- 明明应该停掉的轨迹，又多跑了几步
- 明明应该换分支的轨迹，还沿着旧路线继续扩展

所以 judge 必须分层。

---

## 4. 推荐的 Judge 分层

### 4.1 同步控制型 judge

这类 judge 会直接影响 control flow，必须同步等结果。

v0.1 至少需要两类同步 judge：

#### A. cheap judge

职责：

- runtime 是否成功
- 是否有有效输出图
- 是否空代码
- 是否明显退化 / 重复
- 是否命中 budget 或硬性停止条件

它负责最粗的硬过滤。

#### B. score judge

职责：

- 给当前 step / trajectory 一个可用于控制的 `overall_score`
- 跟上一轮分数做比较
- 决定：
  - 分数太低是否剪枝
  - 两轮分数几乎不变是否早停
  - 分数明显下降是否停掉

这个 judge 可以是：

- 单一 judge model
- 或较轻量的启发式 + 模型混合规则

但它必须足够快，能进入 hot path。

### 4.2 异步分析型 judge

这类 judge 不直接控制当前轮是否继续，而是用于慢分析和最终筛选。

例如：

- weak-model solved count
- committee 投票
- 更昂贵的全轨迹质量评审
- 更细粒度的 exportable 判定

这类 judge 可以慢慢跑，不阻塞当前 trajectory 的主循环。

---

## 5. v0.1 推荐的 Judge 策略

建议 v0.1 直接冻结为：

### 同步部分

每个 runtime step 执行完成后，立刻同步产出至少一条 judge 记录，包含：

- `keep_for_frontier`
- `overall_score`
- `trajectory_progress_score`
- `tool_use_quality_score`
- `note`

同步 judge 的控制规则可以先简单化：

1. runtime 失败 -> `failed`
2. 无有效图 / 空代码 / 明显退化 -> `pruned`
3. `overall_score < low_threshold` -> `pruned`
4. 连续 2 轮 `abs(delta_score) < eps` -> `stopped_early`
5. `delta_score < -drop_threshold` -> `stopped_early` 或 `pruned`
6. budget 用尽 -> `max_step_reached`
7. 否则 -> `keep_for_frontier=true`

### 异步部分

下面这些不必阻塞当前轮：

- weak-model summary
- committee summary
- 更重的 trajectory 级精排
- 复杂 exportable 标签

它们可以在后台回填到 `judge_records` 或导出汇总里。

## 6. 自动化 Pipeline 实际运行起来会是什么样

真正自动化后，它不该是一条从头跑到尾、每步都死等所有模型的串行 bash 脚本。

更合理的形态是：

> 一个持久化到磁盘的状态机 + 多类 worker 队列

### 6.1 热路径主循环

单条 trajectory 的热路径应当是：

1. 从 root sample 初始化 root trajectory
2. planner 产出 `planner_round_xxx.json`
3. 写盘
4. orchestrator 选择当前要执行的 suggestion 第一 step
5. executor 产出 `executor_cot.md` 和 `executor_code.py`
6. 写盘
7. runtime 执行，产出 `runtime_result.json` 和输出图
8. 写盘
9. 同步 cheap judge
10. 同步 score judge
11. 写盘
12. 如果 `keep_for_frontier=true` 且 budget 还够，回到下一轮 planner
13. 否则进入 terminal

### 6.2 冷路径后台任务

同时，后台可以异步处理：

1. weak-model judging
2. committee judging
3. terminal trajectory export
4. quality report / metrics aggregation

所以正确理解是：

- 单条 trajectory 会在某些阶段等待同步 judge
- 但整个系统不应该因为某条轨迹等待重 judge 而停住

---

## 7. 为什么这样仍然可以自动化

你担心“judge model 很多，肯定要等很久，不知道能不能自动化”。

答案是：

> 可以自动化，只要不要把所有 judge 都塞进热路径。

自动化的关键不是“每条 trajectory 完全不停顿”，而是：

- 有明确状态
- 每一步都落盘
- 可以 resume
- 某条 trajectory 在等 judge 时，调度器可以去跑别的 trajectory

所以系统整体仍然是自动化的，只是单条轨迹不是无脑直冲到底。

## 8. 推荐的内部状态机

即使这些状态不一定最终直接写进 schema，orchestrator 内部也应该按这个思路实现。

### 8.1 非终态

- `planner_ready`
- `executor_ready`
- `runtime_ready`
- `waiting_for_sync_judge`
- `running`
- `expanded`

### 8.2 终态

- `answered`
- `pruned`
- `failed`
- `stopped_early`
- `max_step_reached`
- `error`

### 8.3 关键转移

1. `planner_ready -> executor_ready`
2. `executor_ready -> runtime_ready`
3. `runtime_ready -> waiting_for_sync_judge`
4. `waiting_for_sync_judge -> planner_ready`
5. `waiting_for_sync_judge -> terminal`

## 9. V1 的分支策略建议

虽然 schema 和文档都是 branching-capable，但 v0.1 不建议把“planner 全 suggestions 都实例化成 child trajectory 再慢慢回头挑”做得太复杂。

建议直接采用：

- 当前轮先选出 `n` 个要进入 planner 的活跃叶子 trajectory
- 每个 trajectory 的 planner 输出 `k` 个 suggestions，默认 `k=3`
- 当前轮总共会得到 `n * k` 个 candidate suggestions
- 在 **进入 executor 之前**，先做一轮 frontier selection，只保留 `M` 个 suggestion，默认 `M=6`
- 只有这 `M` 个被选中的 suggestion 才真正实例化成 child trajectory，并进入 executor / runtime / judge
- 没被选中的 suggestion **不实例化为 child trajectory**，只保留在当轮 `planner_output.json` 里用于回放和分析

这样做的好处是：

1. 不需要引入 “inactive child trajectory 以后再回来跑” 这层复杂语义
2. 轨迹树只包含真正被执行过或即将被执行的 child
3. frontier 容量控制发生在 executor 之前，更省 runtime 成本

### 9.1 当前轮的推荐筛选规则

建议这一轮先实现最简单可用版：

1. 先从每个父 trajectory 的 `k` 个 suggestions 里取 top-1
2. 如果这样得到的 candidate 数量仍然超过 `M`
   则按全局优先级再截到 `M`
3. 如果这样得到的 candidate 数量少于 `M`
   再从剩余 suggestions 中按全局优先级补满到 `M`

这里的全局优先级在 v0.1 可以先简单定义为：

- 父 trajectory 当前 frontier score
- suggestion 在 planner 输出中的顺序

后面如果需要，再考虑显式加入 suggestion-level score。

### 9.2 父 trajectory 的状态

当一个父 trajectory 的当轮 planner 已经产出 suggestions，且其中部分 suggestion 已被选中并实例化为 child trajectory 后：

- 父 trajectory 自己不再继续追加 step
- `pending_execution = null`
- 后续真正继续推进的是 child trajectory
- 父 trajectory 的 `status` 设为 `expanded`

这里的 `expanded` 表示：

- 这条 trajectory 不是 terminal failure
- 也不是 answered
- 但它已经从“活跃可扩展叶子”变成“树中的内部节点”

因此在 v0.1 中：

- 活跃叶子通常是 `running`
- 已分叉完成、不再直接执行的父节点是 `expanded`

### 9.3 这意味着什么

这套策略和“全 suggestions 先变 child，再保留 active / inactive”相比，更偏：

- planner 先提案
- frontier selector 先过滤
- executor 只执行被选中的 proposal

这更省实现复杂度，也更符合当前 v0.1 目标。

## 11. 下一步最先要做什么

下面是我建议的依赖顺序。

### Step 0：先冻结 5 个决策

先别直接写 orchestrator，先把下面 5 件事冻结：

1. `trajectory_id` 命名规则
2. sample / trajectory / step 目录布局
3. `messages.json` 的真实格式
4. 同步 judge 的最小字段和 stop 规则
5. step 主输出图的语义

如果这 5 个不先定，后面的 store 和 exporter 很容易返工。

本轮冻结结果见：

- `offline_sft_pipeline/docs/9_step0_五项冻结决策_20260329.md`

### Step 1：实现 `core/models.py`

目标：

- 把 5 份 schema 对应成 Python 数据模型

至少需要：

- `RootSample`
- `TrajectoryRecord`
- `PlannerOutput`
- `ExecutorRuntimeResult`
- `JudgeRecord`
- `CanonicalSftSample`

要求：

- 支持校验
- 支持读写 JSON
- 不要让后续逻辑到处操作裸字典

### Step 2：实现 `core/store.py`

这是当前最关键的缺口。

至少需要支持：

1. 从 root sample 初始化 trajectory
2. 保存 / 加载 `trajectory.json`
3. 保存 `messages.json`
4. 保存 planner round 文件
5. 注册 step record
6. 注册 judge record
7. 维护 artifact refs
8. resume

没有 store，runtime 只能单步演示，不能进入自动化系统。

### Step 3：实现 planner / executor / judge client 接口

建议分别做成独立 client，而不是把模型请求写死在 orchestrator 里。

至少要有：

- `planner_client.py`
- `executor_client.py`
- `judge_client.py`

第一版可以先支持：

- stub / fake client
- 单模型 HTTP client

后面再扩成多 provider。

### Step 4：实现 `pipelines/orchestrator_v01.py`

这是第一个真正能“自动跑起来”的模块。

它至少要做：

1. root sample 初始化
2. planner round
3. executor 当前 step
4. runtime 当前 step
5. 同步 judge
6. 更新 trajectory / messages / step records
7. 决定下一轮 planner 或 terminal

建议先实现单叶 top-1 版本。

### Step 5：实现 replay / inspect 工具

至少需要两个脚本：

1. `replay_trajectory.py`
2. `inspect_trajectory.py`

这样调试时才能快速看到：

- planner 当时输出了什么
- executor 执行了哪一步
- runtime 返回了什么
- judge 为什么停掉

### Step 6：实现 exporter

在主循环稳定后，再做：

- `export_terminal_trajectories.py`

先把 terminal trajectories 统一导出成 `canonical_sft_sample_schema.json`。

## 13. v0.1 的最小验收标准

我建议把“自动化 pipeline 第一版可用”定义成下面这 6 条：

1. 一个 root sample 能自动初始化 root trajectory
2. planner 能输出一轮合法 `PlannerOutput`
3. executor 能产出当前 step 的代码和局部 thought
4. runtime 能真实跑出 `runtime_result.json`
5. 同步 judge 能决定继续还是终止
6. terminal trajectory 能导出成 canonical SFT sample

只要这 6 条通了，v0.1 自动化闭环就成立。

---

## 14. 一句话版本

v0.1 最合理的路线不是“所有 judge 同步阻塞”，也不是“所有 judge 异步不管控制逻辑”，而是：

> 轨迹全量存储，terminal 全量导出；cheap judge 和 score judge 同步控制主循环，committee/weak-model judge 异步做补充；先把 top-1 单叶自动化闭环跑通，再逐步打开 branching frontier。
