# fsc147 专项逻辑说明（2026-04-11）

本文整理当前 pipeline 中针对 `fsc147` 的专门处理逻辑，并区分哪些是通用基础设施，哪些是 `fsc147` 特化策略。

## 1. 总览

当前 `fsc147` 相关改动不是全部耦合在一个文件里，而是分成三层：

1. 运行入口层
- 负责 `fsc147` 默认输入、默认 resume 行为、以及运行预算。

2. Orchestrator 策略层
- 负责 `fsc147` 的高分一致 forced final-answer 逻辑。

3. Stop policy 层
- 负责 `fsc147` 轨迹执行后是否继续搜索、是否 early-stop。

另外还有一层是通用评测产物层：
- `sample_results.jsonl` 里的 `no_answer` 状态
- `answered_results.jsonl` 产物

这两项不是 `fsc147` 专属逻辑，但当前主要服务于 `fsc147` smoke / batch 评估。

## 2. 文件分布

### 2.1 运行入口
- `offline_sft_pipeline/scripts/run_fsc147_pipeline.sh`
- `offline_sft_pipeline/scripts/run_dataset_pipeline.py`

这里的 `fsc147` 专项行为包括：
- 默认输入 JSONL 指向 `export_images/output/fsc147/samples.jsonl`
- 默认开启 `resume`
- 对 `source_dataset == "fsc147"` 的 sample，把 `remaining_exec_steps` 压到 3

### 2.2 Orchestrator
- `offline_sft_pipeline/pipelines/orchestrator_v01.py`
- `offline_sft_pipeline/pipelines/api_text_multimodal.py`

这里的 `fsc147` 专项行为包括：
- root / step judge 达到高分且模型答案一致时，触发 `forced_final_answer`
- 下一轮 planner 强制进入 `must_answer_now=True`
- prompt 中会显式暴露 judge 共识候选答案，并要求 planner 的 CoT 与最终答案围绕该答案组织

### 2.3 Stop policy
- `offline_sft_pipeline/eval/stop_policies.py`

这里的 `fsc147` 专项行为包括：
- 不再沿用“只要比上一轮差一点就立刻停”的通用规则
- 改为“基于历史最好分 best_value 的 patience 规则”

## 3. 当前 `fsc147` 处理逻辑

### 3.1 预算
`fsc147` 的默认执行预算为：
- `remaining_exec_steps = 3`

含义：
- 每条轨迹最多允许 3 次 executor step
- 超过预算后，planner 只能进入 answer-only 模式

设计动机：
- count 题常见有效路径是 `count -> verify/rethink -> answer`
- 保持 6 步会明显放大搜索树

### 3.2 forced final-answer 触发条件
当前只对 `fsc147` 生效。

触发条件：
- `overall_score >= 0.98`
- 成功返回的 judge model `normalized_answer` 全一致

触发后行为：
- 下一轮 planner request 设置 `must_answer_now=True`
- `requested_suggestion_count=0`
- prompt 中会明确写入 judge 的候选答案
- prompt 会明确要求：
  - 直接进入 answer mode
  - 最终答案必须等于 judge 候选值
  - top-level `think` 只能论证这个候选值，不能再论证别的数字

这意味着：
- planner 仍然自己生成 CoT 和最终 answer
- 但收到的是更强的 forced handoff，而不是普通的 `must_answer_now`

### 3.3 forced final-answer 的 prompt 注入策略
这是 2026-04-11 调整后的版本。

原因：
- 之前的逻辑只是让 planner 进入 `must_answer_now=True`
- 但 planner 仍可能在最终 answer 中改写 judge 共识答案
- `fsc147_smoke_20260411T201439Z` 的 `fsc147__train__369` 就出现了：judge 共识是 21，planner 最终答成 22

当前修正后：
- 不再在 orchestrator 输出层硬覆盖 `PlannerOutput.direct_answer`
- 改为只通过 planner control prompt 注入更强约束
- prompt 中会显式给出 `candidate_answer`
- prompt 中会显式要求：
  - answer mode
  - 不返回 suggestions
  - final answer 必须等于 `candidate_answer`
  - top-level `think` 也必须围绕这个答案来论证

这样做的原因是：
- 我们希望 CoT 和 answer 一起自洽，而不是只在最后一层把答案“改对”
- 后处理可以基于最终 answer 再做规整，不需要 orchestrator 在这里代替 planner 改写输出

### 3.4 Stop policy
当前 `fsc147` 早停逻辑为：

1. mild regression 不立即停
- 不再因为 `current_value < previous_value` 就立刻 early-stop

2. 两轮不超过历史最高分才停
- 如果连续两次都没有超过 `best_value`
- 则触发 `no_improvement_patience_exhausted`

3. 严重掉分立即停
- 如果 `best_value - current_value >= 0.10`
- 则触发 `severe_regression`

当前阈值：
- `patience = 2`
- `severe_regression_margin = 0.10`

设计意图：
- 给 `enhance`、`mask`、`recount` 这类“第一步不一定立刻涨分”的分支一次纠偏机会
- 同时避免明显走坏的 branch 继续烧 token

## 4. 通用评测产物增强

以下两项是通用 runner 行为，不是 `fsc147` 专属：

### 4.1 `no_answer`
当一个 sample：
- 没有任何 `answered_trajectory_ids`
- 但也不是全 terminal error

则 `sample_results.jsonl` 中的状态为：
- `status = "no_answer"`

这比之前统一记成 `ok` 更适合离线评估。

### 4.2 `answered_results.jsonl`
只汇总有 answered 轨迹的 sample，当前字段为：
- `sample_id`
- `terminal_trajectory_ids`
- `answered_trajectory_ids`
- `pred`
- `answer`
- `score`

用途：
- 直接评估可导出样本
- 不需要再从 `sample_results.jsonl + store` 里二次拼装

## 5. 这些逻辑是离散的还是耦合的

结论：
- 部分离散
- 部分仍有轻度耦合
- 触发范围目前只限 `fsc147`
- 但实现方式仍然是通用框架里的 dataset-specific 分支，不是完全独立 hook

### 5.1 离散的部分
- `run_dataset_pipeline.py` 里的预算切换
- `stop_policies.py` 里的 dataset-specific early-stop
- `run_fsc147_pipeline.sh` 里的专用启动入口

这些都比较容易照抄到别的数据集。

### 5.2 轻度耦合的部分
- `orchestrator_v01.py` 里的 `_maybe_build_forced_final_answer_signal()`
- `api_text_multimodal.py` 里的 forced final-answer prompt handoff

这两处虽然只对 `fsc147` 触发，但它们依赖：
- judge metadata 中的 `model_results` 结构
- planner request metadata 的 handoff 协议

同时：
- `orchestrator_v01.py` 本身并不知道“插件式 dataset policy”
- 而是通过 `source_dataset == "fsc147"` 直接分支
- `stop_policies.py` 也同样是在统一 dispatcher 里判断数据集名

所以如果别的数据集要复用，建议抽成真正的 dataset policy hook，而不是继续在 `fsc147` 分支里堆条件。

## 6. 对其他数据集的扩展建议

如果后续想给别的数据集也加专项逻辑，建议按下面顺序扩：

1. 先在 `stop_policies.py` 中加 dataset-specific 分支
- 这是最独立、最不容易污染主流程的一层

2. 再在 runner 层加 dataset-specific budget
- 比如 OCR-heavy 数据集可以给更高 `remaining_exec_steps`

3. 最后才加 orchestrator answer lock / forced handoff
- 因为这层和 judge metadata 协议耦合更深

## 7. 当前已知风险

1. `forced_final_answer` 目前基于 judge 共识，而不是 ground-truth
- 它适合在 count 模型已经很稳时使用
- 如果 judge backend 本身系统性偏差，会通过更强 prompt 注入被放大

2. `score` 仍是 proxy score
- 对 `fsc147` 当前是相对误差分，不是官方最终指标

3. `fsc147` 的 branch 多样性仍然偏模板化
- 常见是 `count / mask / enhance` 三岔路
- 这会影响 stop policy 的实际收益

## 8. 建议的后续方向

1. 把 `fsc147` 的 forced-answer 逻辑抽象成通用 policy hook
2. 给 planner 做更强的 branch de-dup / low-value branch 抑制
3. 在 `answered_results.jsonl` 之外再补一份 `no_answer_results.jsonl`，专门分析失败模式
