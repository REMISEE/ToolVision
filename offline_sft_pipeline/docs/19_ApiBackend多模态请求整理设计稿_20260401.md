# 19 Step 4：ApiBackend 多模态请求整理设计稿

日期：2026-04-01  
状态：设计稿  
目的：在不大改 `store / orchestrator / schema` 的前提下，明确 `ApiTextBackend` 应该如何把当前的：

- `messages`
- `visible_images`
- `image_artifact_ids`
- `latest_runtime_result`
- `tool_capabilities`

整理成真正发送给多模态模型 API 的请求格式。

---

## 1. 先给结论

当前仓库里的主干已经证明可以工作：

- `PlannerClient`
- `ExecutorClient`
- `JudgeClient`
- `OrchestratorV01`
- `OfflineTrajectoryStore`

但当前 `PlannerClient / ExecutorClient` 生成的 `user_prompt`，本质上仍然是：

- 调试友好的大段文本
- 内嵌多块 JSON

它适合：

- 本地 fake backend
- parser 回归测试
- 调试 request 内容

但它不是后续真实多模态 API 的最佳输入格式。

因此建议把真实 API 接线分成两层：

1. 上层继续保留当前结构化 request
2. `ApiTextBackend` 内部新增一个“多模态整理器”，把结构化 request 转成最终 API payload

也就是说：

> 不要在 `store / orchestrator` 里硬改 message 格式；先在 `ApiTextBackend` 里把现有轻结构 request 重新编译成真正的多模态请求。

---

## 2. 当前输入到底是什么

### 2.1 Planner 当前拿到的输入

当前 `PlannerClientRequest` 包含：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `question`
- `messages`
- `visible_images`
- `budget`
- `tool_capabilities`
- `latest_runtime_result`
- `requested_suggestion_count`

对应代码：

- `offline_sft_pipeline/pipelines/request_models.py`

### 2.2 Executor 当前拿到的输入

当前 `ExecutorClientRequest` 包含：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `step_idx`
- `question`
- `messages`
- `visible_images`
- `suggestion_id`
- `suggestion_step_index`
- `step_spec`
- `planner_global_chain_cot`
- `suggestion_cot`
- `tool_capabilities`

### 2.3 当前 message 里有什么

当前 `messages.json` 每条消息只有轻结构：

- `role`
- `content`
- `image_artifact_ids`
- `metadata`

其中：

- `image_artifact_ids` 只是 artifact 引用
- 它不是图片实体
- 它也不直接包含 path/url

### 2.4 当前 `visible_images` 是什么

当前 `visible_images` 是结构化图片实体列表：

- `artifact_id`
- `path`
- `media_type`
- `width`
- `height`

当前 orchestrator 规则是：

1. 所有 root images
2. 最近一步主输出图

即：

- `visible_images` 更像“当前 step 的候选输入图集合”
- 不是“历史消息全量图集合”

---

## 3. 当前主要问题

当前直接把这些东西拼进 user prompt，会有 4 个问题。

### 3.1 message 和 image 是分离的

模型真正需要的是：

- 某条 message 对应哪些图片

而当前给到 prompt 的是：

- `messages_json`
- `visible_images_json`

两者之间还要靠 `image_artifact_ids` 再做一次人工关联。

### 3.2 JSON 太重

以下几块直接原样塞 JSON，token 成本和阅读负担都高：

- `messages_json`
- `visible_images_json`
- `budget_json`
- `latest_runtime_result_json`
- `tool_capabilities_json`

### 3.3 调试字段和模型字段混在一起

像这些字段主要是调试/追踪用途：

- `sample_id`
- `trajectory_id`
- 某些 path
- 某些内部 id

它们不一定值得原样暴露给模型。

### 3.4 当前 prompt 里“历史图”和“当前工作图”没有明确分层

模型看到图片时，实际上有两类语义不同的图：

1. 历史消息里关联过的图
2. 当前 step 可作为输入起点的图

这两类图目前没有被显式区分。

---

## 4. 设计目标

这版设计稿的目标是：

1. 不改 `store` 的落盘格式
2. 不改 `Trajectory / Message / RuntimeResult` schema
3. 不要求 orchestrator 直接产出多模态 API payload
4. 由 `ApiTextBackend` 独立完成 request 整理
5. planner 和 executor 都能拿到：
   - 完整消息历史
   - 关联图片
   - 当前候选输入图
   - 控制字段
   - 工具目录

---

## 5. 建议的整体分层

建议把真实文本 backend 逻辑拆成 3 层。

### 5.1 上层 client

保持现状：

- `PlannerClient`
- `ExecutorClient`

它们仍然接收当前结构化 request。

### 5.2 中间整理层

新增：

- `PlannerMultimodalRequestBuilder`
- `ExecutorMultimodalRequestBuilder`

职责：

- 解析 `messages + visible_images + image_artifact_ids`
- 解析 artifact id 到真实 path/url
- 构造规范化的多模态请求对象

### 5.3 最底层 provider adapter

新增：

- `OpenAITextVisionAdapter`
- 或其他厂商 adapter

职责：

- 把规范化的多模态请求对象编译成具体厂商 API payload

也就是说：

> `ApiTextBackend` 应该先做“规范化多模态对象”，再做“厂商 API 编译”，不要直接从当前 JSON prompt 文本拼到具体 API。

---

## 6. 核心对象：规范化多模态请求

建议在 backend 内部使用一个统一中间对象。

```json
{
  "stage": "planner",
  "system_instruction": "string",
  "conversation": [
    {
      "role": "user",
      "content": [
        {"type": "input_text", "text": "What number is written on the hanging tag?"},
        {"type": "input_image", "artifact_id": "img_root_0", "path": "..."}
      ],
      "metadata": {
        "message_kind": "user_question",
        "message_id": "m_user"
      }
    }
  ],
  "current_images": [
    {
      "artifact_id": "img_root_0",
      "path": "...",
      "role": "root"
    },
    {
      "artifact_id": "img_step_001_0",
      "path": "...",
      "role": "latest_primary"
    }
  ],
  "control": {
    "requested_suggestion_count": 3,
    "budget": {
      "remaining_rounds": 2,
      "remaining_children": 2,
      "remaining_steps": 3
    },
    "latest_runtime_result_summary": {
      "success": true,
      "text": "cropped serial region",
      "observed_helper_calls": ["ground_box", "dino_crop"]
    }
  },
  "tools": [
    {
      "name": "ground_box",
      "description": "..."
    }
  ],
  "response_contract": {
    "format": "planner_v01"
  },
  "debug_context": {
    "sample_id": "demo__train__0001",
    "trajectory_id": "traj__demo__train__0001__root__r000_s2",
    "round_idx": 1
  }
}
```

这里要特别注意：

- `conversation` 是历史消息
- `current_images` 是当前 step 的候选输入图集合
- `debug_context` 默认不直接喂给模型，除非特定 provider 需要

## 7. artifact 解析规则

这是这次设计里最关键的部分。

### 7.1 目标

把：

- message 里的 `image_artifact_ids`

解析成：

- 模型最终能看到的真实图片项

### 7.2 建议规则

新增一个内部 resolver：

- `ArtifactResolver`

最小接口建议：

```python
resolve_message_artifacts(
    *,
    messages: list[ConversationMessage],
    visible_images: list[ImageArtifactRef],
    latest_runtime_result: ExecutorRuntimeResult | None,
    sample_id: str,
    trajectory_id: str,
) -> dict[str, ResolvedArtifact]
```

### 7.3 解析来源优先级

按下面优先级解析 artifact id：

1. `visible_images`
2. `latest_runtime_result.images`
3. root artifacts
4. 当前 trajectory 历史 step 的 `runtime_result.images`

短期实现上，建议：

- 先至少保证能解析 `visible_images` 和当前历史里已引用过的 step 输出图

### 7.4 解析结果

`ResolvedArtifact` 最少保留：

- `artifact_id`
- `path`
- `media_type`
- `width`
- `height`
- `source`

其中 `source` 可取：

- `root`
- `runtime_output`
- `visible_image`

## 8. planner 请求怎么整理

### 8.1 发送给模型的内容建议分 5 块

#### A. system instruction

保留：

- planner 角色
- 输出协议
- `<think> + <answer>/<suggestions>` 规则
- suggestion JSON shape

这部分可直接复用现有：

- `planner_system_v01.txt`

#### B. conversation history

做法：

1. 遍历 `messages`
2. 每条消息保留：
   - `role`
   - `content`
3. 如果该 message 带 `image_artifact_ids`
   - 先把 artifact id 解析成真实图片
   - 再把图片贴到该 message 对应内容里

建议多模态内容顺序：

1. 先图片
2. 后文本

原因：

- 模型更容易把“这条 message 关联的图”与文本绑定在一起

#### C. current images

对 planner，`current_images` 仍然建议单独保留一块。

原因：

- 历史消息里的图是“过去看过的图”
- `current_images` 是“本轮 planning 当前明确可参考的图”

建议在 planner 的最后再附一条 user message：

- "Current candidate input images for this round:"
- 再列出这些图

#### D. control state

planner 必须看到：

- `requested_suggestion_count`
- `budget`
- `latest_runtime_result_summary`

但建议从大 JSON 改成精简摘要文本。

示例：

```text
Planning control:
- requested_suggestion_count: 3
- remaining_rounds: 2
- remaining_children: 2
- remaining_steps: 3
- latest_runtime_success: true
- latest_runtime_text: cropped serial region
- latest_helper_calls: ground_box, dino_crop
```

#### E. tool catalog

只保留：

- 工具名
- 一句描述
- 必要 usage note

不要把完整 JSON schema 全塞进去，除非具体模型真的需要。

### 8.2 planner 不建议直接看到的字段

以下字段建议默认不进入模型正文：

- `sample_id`
- `trajectory_id`
- 各种本地 path
- 内部 message id

这些可以放在：

- adapter 日志
- request tracing metadata

## 9. executor 请求怎么整理

executor 和 planner 不一样的地方在于：

- executor 需要更强的“当前一步执行说明”
- 不需要 `budget`
- 但需要 `step_spec`、`planner_global_chain_cot`、`suggestion_cot`

### 9.1 executor 建议分 5 块

#### A. system instruction

保留现有：

- `<think> + <code>` 协议
- 只能输出一步代码
- 用 `result` 保留主图

#### B. conversation history

和 planner 一样：

- 消息按 `role + text + 关联图片` 发送

#### C. current candidate images

executor 也要看到当前候选输入图集合。

但这里建议加一个明确提示：

```text
The runtime will start from current_active_image_index = 1 unless your code explicitly uses another returned image object.
```

也就是：

- 让 executor 知道“候选图不止一张”
- 但默认起手图是哪张也要说清楚

#### D. execution instruction block

必须保留：

- `planner_global_chain_cot`
- `suggestion_cot`
- `step_spec`

建议整理成更直白文本：

```text
Execution target:
- suggestion_id: s21
- step_id: step_ocr_from_crop
- step_goal: Read the serial digits from the existing crop.

Planner rationale:
- global: ...
- selected suggestion: ...

Required capabilities:
- ocr_assist
```

#### E. tool catalog

和 planner 一样，保留紧凑版工具目录。

## 10. 当前 message 和 current_images 的关系怎么处理

这个点最容易混淆，建议明确成下面规则。

### 10.1 message 中的图片

message 中图片表示：

- “这条历史消息绑定了哪些图”

它的语义是：

- 历史证据
- 历史上下文

### 10.2 `current_images`

`current_images` 表示：

- 当前 step 候选输入图集合

它的语义是：

- 当前轮 planning/execution 可直接参考的图
- runtime 可用来决定 `image_index` 的图

### 10.3 两者不建议在存储层合并

原因：

- message 图片是历史绑定关系
- current_images 是当前执行上下文
- 两者语义不同

### 10.4 但建议在 backend 发送给模型时“表现上融合”

也就是说：

- 存储层不合并
- 发送给模型时，可以同时做：
  - 历史 message 中插入其关联图
  - 最后再单独追加 `current_images`

这就是“逻辑不合并，展示上融合”。

---

## 11. 对 `visible_images` 的建议

当前不建议马上改 orchestrator 里的 `visible_images` 规则。

保持当前：

- root images
- latest primary image

原因：

1. 它已经和 runtime 的 `image_index` 选择逻辑对齐
2. 它已经被测试验证
3. 当前主要问题不是“可见图不够”，而是“图片没有被整理成好用的多模态消息”

短期更合适的做法是：

- 保持 `visible_images` 作为当前候选输入图集合
- 在 backend 端把历史消息关联图也补进去

这样你就同时有：

- 历史全记录
- 当前工作图集合

---

## 12. provider adapter 的最小接口建议

建议 `ApiTextBackend` 不直接吃 prompt 字符串，而是先吃规范化对象。

例如：

```python
class ApiTextBackend:
    def generate_from_multimodal_request(
        self,
        *,
        stage: Literal["planner", "executor"],
        request: NormalizedMultimodalRequest,
    ) -> BackendResponse:
        ...
```

然后短期兼容层可以保留原有：

```python
def generate(...):
    # 兼容 scripted / 旧逻辑
```

如果不想马上改 protocol，也可以先在 backend 内部新增私有方法：

- `_build_planner_multimodal_request(...)`
- `_build_executor_multimodal_request(...)`

---

## 13. 建议的落地顺序

### 第一步

先不改 `store / orchestrator / schema`。

### 第二步

在 backend 内新增：

- `ArtifactResolver`
- `PlannerMultimodalRequestBuilder`
- `ExecutorMultimodalRequestBuilder`

### 第三步

先做一个“调试输出模式”：

- 不实际调模型
- 只把整理后的多模态请求写成 JSON

例如落到：

- `planner_compiled_request.json`
- `executor_compiled_request.json`

这样先检查：

- 历史消息是否完整
- 图片是否都被正确挂到对应 message
- `current_images` 是否合理

### 第四步

再接具体 provider adapter。

---

## 14. 一句话方案

当前最合理的方案不是去大改 `messages.json` 或强行把 `visible_images` 塞回 store，而是：

> 保留现有轻结构存储；在 `ApiTextBackend` 内新增一个多模态整理层，把 `messages + image_artifact_ids + visible_images + latest_runtime_result + tool_capabilities` 编译成“历史 message 带图 + 当前候选图 + 控制字段 + 工具目录”的标准化多模态请求，再交给具体模型 API。
