## 1. 先给结论

当前仓库里已经有一条可以运行的最小多轮 branching pipeline 主循环：

- `planner -> selection -> child fork -> executor -> runtime -> message writeback -> judge -> next frontier`

但它现在分成两层理解：

### 1.1 已经落地、已经可测的部分

这些现在已经在代码里：

- `RootSample / Trajectory / Messages / PlannerOutput / StepRecord / JudgeRecord` 这一整套 schema 和 store
- `PlannerClient / ExecutorClient / JudgeClient`
- `OrchestratorV01`
- 单步 runtime wrapper smoke
- helper runtime smoke
- 用 fake/scripted 结果驱动的多轮 orchestrator 回归测试

### 1.2 还没落地成“真实单命令大 pipeline”的部分

这些现在还没真正接好：

- `ApiTextBackend`
  - 真实 planner / executor 模型调用还没接
- `CommitteeJudgeBackend`
  - 真实 judge committee 还没接
- `run_single_sample_pipeline.py`
  - 还没有一个正式入口把真实 backend、真实 runtime、store、orchestrator 全接成一条命令

所以当前正确结论不是：

- “完全不能跑”

而是：

- “fake 结果驱动的多轮循环现在已经能跑”
- “真实模型调用版的完整多轮 pipeline 还没接线完”

## 2. `test_orchestrator_v01.py` 是做什么的

这次新增的：

- `offline_sft_pipeline/tests/test_orchestrator_v01.py`

它不是生产代码，也不是 demo 脚本。

它的职责是：

> 用确定性的 scripted planner / executor / runtime / judge，把 `OrchestratorV01` 的执行语义钉死成回归测试。

它主要验证 3 类事情：

1. 多轮 branching 能不能真的继续往下跑
2. `messages / visible_images / latest_runtime_result / budget / M-selection` 这些关键语义是否符合当前实现
3. 一些边界条件是否按当前文档收束

当前这个 test 不是在测：

- 真实模型质量
- 真实 helper 服务质量
- 真实 OCR / SAM / crop 效果

它是在测：

- orchestration 语义
- store 落盘
- trajectory 状态流转
- 多轮 child 上下文继承

也就是说：

> `test_orchestrator_v01.py` 的价值是“把 v01 orchestrator 的语义固定下来，后面改代码时不把它悄悄改坏”。

## 3. 为什么真实的多轮 pipeline 还没有完全落地

这里要拆开说，不然很容易把“没有真实大模型接线”和“不能多轮循环”混成一件事。

### 3.1 不是 orchestrator 主循环没有

主循环已经有了：

- root 初始化
- planner 调用
- 全局 selection
- child fork
- executor 调用
- runtime 调用
- messages 写回
- judge 调用
- frontier 推进

所以缺口不在：

- “有没有主循环”

### 3.2 当前真实缺的是 3 个接线点

#### A. 真实 planner / executor 文本生成 backend

当前：

- `PlannerClient`
- `ExecutorClient`

都已经有 prompt build 和 parse 逻辑。

但底层真实文本 backend：

- `ApiTextBackend`

还是：

- `NotImplementedError`

所以现在不能直接拿真实模型去跑 planner / executor。

#### B. 真实 judge backend

当前：

- `JudgeClient`

已经能把后端分数转成：

- `JudgeRecord`

但：

- `CommitteeJudgeBackend`

还是：

- `NotImplementedError`

所以真实 judge 集成还没完成。

#### C. 正式的单样本入口脚本

当前没有一个正式脚本把下面这些一次性接起来：

- sample loader
- store run root
- planner backend
- executor backend
- runtime wrapper
- judge backend
- orchestrator
- export

这就是为什么你现在还没有：

- 一条“真实模型 + 真实 runtime + 真实 judge”的完整单命令多轮 pipeline

### 3.3 runtime 本身不是完全没做

runtime 这边不能说没做。

当前已经有：

- `run_single_runtime_smoke.py`
- `run_runtime_helper_smoke.py`

也就是说：

- 单步 runtime wrapper 已有 smoke
- helper runtime 已有 smoke

现在缺的是：

- 把它作为正式 runtime backend 接进真实多轮主循环入口

## 4. 如果不考虑真实模型，只用 fake 结果，能不能跑多轮

答案是：

> 可以。

而且现在已经不是“理论上可以”，而是：

- 已经有回归测试证明可以

### 4.1 当前能跑到什么程度

用 scripted / fake 的 planner / executor / runtime / judge 结果，当前已经能跑：

1. root round 产出多条 suggestion
2. 按 `M` 做全局 selection
3. fork 多个 child trajectories
4. child 执行一步
5. child 回到下一轮 planner
6. 下一轮继续产出 suggestion 或直接回答
7. 再 fork / 再执行
8. 最后进入 `answered / failed / pruned / max_step_reached`

### 4.2 这次回归里实际覆盖了一个 3 轮场景

当前测试里的复杂场景大意是：

#### Round 0

root planner 产出 3 条 suggestion：

- `s1`
- `s2`
- `s3`

三条都被执行成 child trajectories。

#### Round 1

- `s1` 这条 child 直接回答
- `s2` 这条 child 在 rethink 后给出两条分叉：
  - 一条继续沿用前一步工具结果
  - 一条改写前一步工具链后再做
- `s3` 这条 child 也给出两条分叉：
  - 一条 retry 当前路径
  - 一条换策略

然后按 `M=3` 做全局选择，只选中：

- `s21`
- `s31`
- `s22`

没选中的：

- `s32`

只保留在 planner output，不会真的执行。

#### Round 2

- `s21` 直接回答
- `s31` runtime 失败
- `s22` 再执行一步后因预算用尽收束

这已经是一个真实的：

- 多 parent
- 多 suggestion
- 多轮 planner
- 多轮 runtime
- direct answer / runtime fail / budget stop 混合

的回归用例。

## 5. 当前 pipeline 的分层结构

当前可以把 pipeline 分成 6 层。

### 5.1 数据层

主要对象：

- `RootSample`
- `TrajectoryRecord`
- `MessagesDocument`
- `PlannerOutput`
- `StepRecord`
- `JudgeRecord`
- `ExecutorRuntimeResult`

### 5.2 Store 层

主要模块：

- `offline_sft_pipeline/core/store.py`

职责：

- 建目录
- 初始化 root / child trajectory
- 保存和加载 `messages.json`
- 保存和加载 planner output
- 保存和加载 runtime result
- 注册 step / judge / status 更新

### 5.3 Client 层

主要模块：

- `PlannerClient`
- `ExecutorClient`
- `JudgeClient`

职责：

- 把 structured request 转成 prompt / backend 调用
- 解析模型输出
- 变成结构化对象

### 5.4 Runtime 层

主要职责：

- 执行 executor code
- 写出 `runtime_result.json`
- 写出输出图和 stdout/stderr

### 5.5 Orchestrator 层

主要模块：

- `OrchestratorV01`

职责：

- 调度 planner / executor / runtime / judge
- 做 frontier selection
- fork child trajectories
- 推进多轮循环

### 5.6 Tests / Smoke 层

现在有两类：

- runtime smoke
- orchestrator semantic regression

## 6. 当前一条样本怎么跑

下面按真实代码顺序讲。

### 6.1 输入：`RootSample`

最上游输入是：

```python
RootSample(
    sample_id="textvqa__train__000001",
    question="价格标签上写的数字是多少？",
    images=[...],
)
```

### 6.2 `store.init_root_trajectory(...)`

orchestrator 先做：

1. 保存 `root_sample.json`
2. 复制 root image 到 sample artifacts
3. 初始化 root trajectory
4. 初始化 root `messages.json`

### 6.3 初始 messages

当前 root 初始 messages 只有两条：

1. `system`
2. `user`

这里的 `user` message 会挂 root image artifact ids。

### 6.4 进入 planner

对每个 `running` trajectory：

1. 取当前 `messages`
2. 取当前 `visible_images`
3. 取当前 `budget`
4. 取 `latest_runtime_result`
5. 组装 `PlannerClientRequest`
6. 调 `planner_client.run(...)`

### 6.5 selection

这一轮所有 parent trajectories 的 planner outputs 会汇总后做全局 selection。

当前规则是：

1. 每个 parent 先拿 top-1 suggestion
2. 如果 top-1 数量已经超过 `M`
   - 截断到 `M`
3. 如果 top-1 数量少于 `M`
   - 再从剩余 suggestions 里按优先级补满

### 6.6 child fork

被选中的 suggestion 会：

1. 生成 child trajectory id
2. 生成 `ForkProvenance`
3. 生成 `PendingExecution`
4. 复制 parent 历史
5. 初始化 child budget

### 6.7 executor

每条 child 当前只执行：

- suggestion 的第 1 步

不会顺着旧 suggestion 自动把第 2 步、第 3 步连续跑完。

### 6.8 runtime

executor 产出 code 后：

1. 写 `executor_cot.md`
2. 写 `executor_code.py`
3. 调 runtime
4. 让 runtime 写：
   - `runtime_result.json`
   - `stdout.txt`
   - `stderr.txt`
   - 输出图

### 6.9 message writeback

runtime 回来后：

1. 追加一条 assistant step message
2. 追加一条 tool result message

### 6.10 step record

然后注册：

- `StepRecord`

### 6.11 judge

再调：

- `JudgeClient`

得到：

- `JudgeRecord`

### 6.12 trajectory status update

最后根据：

- runtime success
- runtime 内容
- judge keep
- budget

决定 child trajectory 的新状态。

### 6.13 frontier 推进

如果 child 还能继续：

- status = `running`

则进入下一轮 frontier。

否则：

- 进入 terminal 集合

## 7. 当前各阶段到底传什么参数

这一节只按当前实现写，不写目标态。

## 7.1 Planner 阶段

### 输入对象

- `PlannerClientRequest`

当前字段：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `question`
- `messages`
- `visible_images`
- `budget`
- `tool_capabilities`
- `latest_runtime_result`
- `requested_suggestion_count`
- `metadata`

### 这些字段当前分别从哪来

#### `sample_id`

- 当前 trajectory 的 sample id

#### `trajectory_id`

- 当前正在 planning 的 trajectory id

#### `round_idx`

- `trajectory.latest_planner_round_idx + 1`
- 如果还没有 planner history，则是 `0`

#### `question`

- 直接取 trajectory 上的 question

#### `messages`

- 直接读取当前 trajectory 的 `messages.json`

#### `visible_images`

当前规则固定为：

1. 所有 root images
2. 最新一步主输出图

其中主输出图定义为：

- 最近一步 `runtime_result.images[0]`

#### `budget`

- 当前 trajectory 的 budget 快照

#### `tool_capabilities`

- 当前 config 里传进来的工具能力目录

#### `latest_runtime_result`

- 当前 trajectory 最近一步的 `runtime_result.json`
- 如果还没执行过 step，则为 `None`

#### `requested_suggestion_count`

当前是：

- 如果还有 `child budget` 且还有 `step budget`
  - `min(k, remaining_children)`
- 否则
  - 不请求 suggestion
  - 具体传值为 `None`

注意：

- “不请求 suggestion” 不等于“不调 planner”
- 即使没有 child/step budget，planner 仍然会被调用
- 只是这时 orchestrator 只允许它做“能不能直接回答”的判断

### Planner 输出对象

- `PlannerOutput`

当前字段：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `created_at`
- `can_answer_now`
- `global_chain_cot`
- `direct_answer`
- `stop_reason`
- `suggestions`

### 当前 planner 响应协议

planner 返回文本必须是：

1. `<think>...</think>`
2. 然后是下面两种二选一：
   - `<answer>...</answer>`
   - `<suggestions>[...]</suggestions>`

### `suggestions` 当前结构

每条 suggestion 现在有：

- `suggestion_id`
- `suggestion_cot`
- `steps`

每个 step 有：

- `step_id`
- `step_goal`
- `capability_plan`
- `executor_instruction`

---

## 7.2 Selection 阶段

这个阶段没有单独 client。

输入是：

- 当前轮所有 `_PlannerRoundContext`

当前只看这些信息：

- `planner_output.can_answer_now`
- `requested_suggestion_count`
- `planner_output.suggestions`
- parent 的最近 judge score
- suggestion 顺序
- parent trajectory id

输出是：

- 被选中的 `_FrontierCandidate` 列表

这一步不写消息，但会影响：

- 哪些 suggestion 真的会变成 child trajectories

---

## 7.3 Child Fork 阶段

输入是：

- 一个被选中的 `_FrontierCandidate`

会构造的对象有：

### `ForkProvenance`

字段：

- `parent_trajectory_id`
- `parent_planner_round_idx`
- `parent_suggestion_id`

### `PendingExecution`

字段：

- `planner_round_idx`
- `suggestion_id`
- `suggestion_step_index`
- `step_id`

### child budget

当前 child budget 规则是：

- `remaining_rounds = parent.remaining_rounds - 1`
- `remaining_children = parent.remaining_children - 1`
- `remaining_steps = parent.remaining_steps`

### child 会复制什么

现在 child 初始化时会复制 parent 的：

- `messages`
- `planner` 历史文件
- `steps` 历史文件
- `judge` 历史文件
- `trajectory` 里的 planner_history / step refs / judge refs

这次之所以专门补了这一点，是因为如果只复制路径元数据、不复制实际文件，child 下一轮就读不到：

- 最新主图
- 最新 runtime result

也就谈不上“看到前面的工具调用”。

---

## 7.4 Executor 阶段

### 输入对象

- `ExecutorClientRequest`

当前字段：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `step_idx`
- `question`
- `messages`
- `visible_images`
- `suggestion_id`
- `suggestion_step_index`
- `step_spec`
- `planner_global_chain_cot`
- `suggestion_cot`
- `tool_capabilities`
- `metadata`

### 这些字段当前分别从哪来

#### `messages`

- 当前 child trajectory 的 `messages.json`

#### `visible_images`

- 当前 child trajectory 的可见图
- 规则仍然是：
  - 所有 root images
  - 当前 child 继承到的最新主图

#### `suggestion_id`

- 当前被执行的 suggestion id

#### `suggestion_step_index`

- 当前固定为 `0`

#### `step_spec`

- 当前 suggestion 的 `steps[0]`

#### `planner_global_chain_cot`

- 来自当前轮 `PlannerOutput.global_chain_cot`

#### `suggestion_cot`

- 来自当前 suggestion 的 `suggestion_cot`

也就是说：

> planner global CoT 和 suggestion CoT 虽然不进 `messages.json`，但它们确实会作为结构化字段继续传给 executor。

### Executor 输出对象

- `ExecutorStepOutput`

字段：

- `cot`
- `code`
- `raw_response_text`
- `metadata`

### 当前 executor 响应协议

executor 返回文本必须是：

1. `<think>...</think>`
2. `<code>...</code>`

### 当前 executor 输出落盘

当前 orchestrator 会把 executor 输出拆成两个文件：

- `executor_cot.md`
- `executor_code.py`

---

## 7.5 Runtime 阶段

### 输入对象

- `RuntimeStepRequest`

字段：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `step_idx`
- `executor_cot_path`
- `executor_code_path`
- `visible_images`
- `step_output_dir`
- `image_index`

### 当前 `image_index` 怎么选

规则是：

- 如果有最新主图，就优先把它作为当前默认输入图
- 否则用第 0 张图

所以当前运行 executor code 时，默认 `image` 会尽量对应：

- 最新一步主输出图

### Runtime 输出对象

- `RuntimeStepOutput`

当前 orchestrator 真正依赖的是其中的：

- `runtime_result`

而 `runtime_result` 会进一步解析成：

- `ExecutorRuntimeResult`

字段包括：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `step_idx`
- `created_at`
- `success`
- `images`
- `text`
- `meta`
- `observed_helper_call_count`
- `observed_helper_calls`
- `code_execution`
- `error`

### runtime 阶段落盘

当前默认 step 目录里至少会有：

- `executor_cot.md`
- `executor_code.py`
- `runtime_result.json`
- `stdout.txt`
- `stderr.txt`
- 输出图文件

---

## 7.6 Judge 阶段

### 输入对象

- `JudgeClientRequest`

当前字段：

- `sample_id`
- `trajectory_id`
- `scope_type`
- `scope_step_idx`
- `judge_stage`
- `question`
- `messages`
- `visible_images`
- `planner_output`
- `step_record`
- `runtime_result`
- `final_answer`
- `metadata`

### 当前 step judge 调用时实际传的内容

当前 orchestrator 在 step judge 时传的是：

- `scope_type = "step"`
- `scope_step_idx = 当前 step_idx`
- `judge_stage = config.judge_stage`
- `messages = 追加完 assistant/tool message 之后的完整 messages`
- `visible_images = post-step 的 visible images`
- `planner_output = 当前轮 planner output`
- `step_record = 当前 step record`
- `runtime_result = 当前 step runtime result`
- `final_answer = None`

### Judge 输出对象

- `JudgeRecord`

当前热路径真正依赖的是：

- `overall_score`
- `keep_for_frontier`
- `exportable`
- `note`

### 当前 judge policy

默认策略很简单：

- `overall_score >= 0.25`
  - `keep_for_frontier = true`
- 只有 trajectory-level 且分数更高时才会 `exportable = true`

当前 orchestrator 只用到了：

- `keep_for_frontier`

## 8. 当前 `messages` 到底包含什么

这是最容易误解的一节。

### 8.1 当前 `messages.json` 是什么

它是：

> 单条 trajectory 的已执行历史账本。

不是：

- planner proposal 的全集
- 所有 CoT 的全集
- judge 历史账本

### 8.2 当前一定会进 `messages` 的内容

#### A. root 初始两条

1. system instruction
2. user question

#### B. 每执行一步追加两条

1. assistant
   - 里面包含 executor CoT
   - 里面包含 `<tool_call name="code_image_tool"> ...code... </tool_call>`
2. tool
   - 里面包含 runtime 返回的 text
   - 里面挂 runtime 输出图 artifact ids

#### C. direct answer 时追加一条

- assistant final answer

### 8.3 当前不会进 `messages` 的内容

#### A. planner global CoT

不直接进 `messages`

#### B. suggestion CoT

不直接进 `messages`

#### C. planner 输出的所有 proposals

不直接进 `messages`

#### D. judge record

不进 `messages`

### 8.4 这是不是意味着 message “什么都有”

不是。

更准确地说：

- 对“执行历史”来说，`messages` 现在已经够全
- 对“所有推理分层”来说，`messages` 不是全集

当前真正的存储分层是：

#### 执行账本

- `messages.json`

#### proposal/history

- `planner/round_xxx.json`

#### executor 细节文件

- `executor_cot.md`
- `executor_code.py`

#### runtime 结果

- `runtime_result.json`

#### judge 结果

- `judge/*.json`

### 8.5 现在这套 message 设计合不合理

按当前 v01 的目标，我认为是合理的。

理由是：

1. planner 输出本质上是 proposal，不是已执行事实
2. 一个 planner round 可能会给多条 suggestion，其中大部分不会真的执行
3. 如果把所有 planner proposal 都写进 `messages`，就会污染 trajectory transcript

所以当前更合理的理解是：

- `messages` 存已执行链
- planner global/suggestion CoT 存 proposal 层
- executor CoT + code 一部分进 messages，一部分进 step 文件

如果以后训练样本真的想要三层 CoT 合并成一条完整监督链，更好的地方是：

- exporter

而不是：

- 直接改 raw `messages.json`

## 9. 当前 visible images 规则

### 9.1 现在不是“只保留第一张和最后一张”

当前真实规则是：

1. 保留所有 root images
2. 再加最新一步主输出图

所以如果 sample 本来就只有 1 张 root image，那么看起来近似于：

- 第一张 root 图
- 最后一张中间图

但如果 sample 有多张 root image，当前不会只保留第一张。

### 9.2 为什么当前这么做

因为当前实现想兼顾：

- root 原始上下文不丢
- 最新中间结果也能继续被 planner / executor 使用

### 9.3 主输出图怎么定义

当前固定定义为：

- 最近一步 `runtime_result.images[0]`

辅助图虽然也会保存，但不默认继续带到下一轮。

## 10. 当前状态流转规则

### 10.1 parent trajectory

如果某轮 planner 后至少有一条 suggestion 被实例化成 child：

- parent -> `expanded`

### 10.2 child trajectory

执行完一步并过 judge 后：

#### `failed`

当：

- `runtime_result.success = false`

#### `pruned`

当：

- runtime 成功，但没有图片且没有有效文本
- 或 judge `keep_for_frontier = false`

#### `max_step_reached`

当：

- `remaining_steps <= 0`
- 或 `remaining_rounds <= 0`

#### `running`

其余情况

### 10.3 direct answer

如果 planner `can_answer_now = true`：

- 追加 final answer message
- trajectory -> `answered`

### 10.4 无 child/step budget 但 planner 没直接回答

现在行为是：

1. 仍然调 planner
2. `requested_suggestion_count = None`
3. suggestion 不会进入 selection/execution
4. trajectory -> `max_step_reached`

## 11. 当前 `stopped_early` 的一个现实限制

这个点很重要。

从当前实现看，selection 是：

- 每个 parent 先保 top-1
- 再拿剩余 suggestion 补满 `M`

而每一轮真正进入下一轮 frontier 的 trajectories 总数本来就不会超过 `M`。

这意味着：

> 在正常健康路径下，全局 `M` 更常裁掉的是“同一 parent 的额外 suggestion”，而不是把整个 parent 从 frontier 里淘汰掉。

所以当前真实表现通常是：

- direct answer
- failed
- pruned
- max_step_reached

而不是大量：

- `stopped_early`

如果你以后想看到更强的 parent-level 淘汰，就需要再设计：

- 更 aggressive 的 selection policy

## 13. 这次新增测试的真正意义

这次新增的 orchestrator test 不只是“补了个测试文件”。

它实际上逼出了两个真实实现缺口：

### 13.1 child 没继承到最新 planner round 状态

如果 child 是从旧 parent record fork 出来，child 下一轮 planner 的：

- `round_idx`

会错。

现在已经修成：

- child 从已注册当前 planner round 的 parent 复制

### 13.2 child 没复制 parent 的历史文件

如果只复制 trajectory 里的路径字符串，但不复制实际文件，child 下一轮就读不到：

- 最新 runtime result
- 最新主图

现在也已经补上了：

- planner / steps / judge 历史文件复制

这两个补丁说明：

> 当前最大的价值不是“终于证明 fake 能跑”，而是它把 v01 里真正会阻断多轮的实现问题提前暴露并修掉了。
