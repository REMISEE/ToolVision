## 5. 关于 executor output 的当前结论

这里要特别说明一件事：

- `executor_runtime_result_schema.json` 不是 executor 模型输出 schema
- 它是 runtime 执行结果 schema

当前 executor 这一侧，真正需要承接的是：

- `cot`
- `code`

因此当前新增的承接对象是：

- `ExecutorStepOutput`

它的定位是：

> executor client / parser 把原始模型文本解析后，先落到 `ExecutorStepOutput`，再由 store 写成 `executor_cot.md` 和 `executor_code.py`。

这意味着：

- runtime 不负责从模型原始文本里拆 code
- runtime 只消费已经落盘好的 `executor_code.py`
- executor client 以后要负责“原始返回 -> `ExecutorStepOutput`”

### 5.1 `ExecutorStepOutput` 为什么现在不带 `step_id / step_idx / sample_id`

因为它的职责不是“描述整条 step 记录”，而只是承接 executor 模型这一次真正生成出来的内容：

- `cot`
- `code`
- 可选 `raw_response_text`
- 可选 parser metadata

而 step 上下文和轨迹身份信息，当前已经由别的对象承接：

- 执行前要跑什么：`PendingExecution`
- 执行后这一步怎么登记进 trajectory：`StepRecord`
- 这一步真实执行出了什么：`ExecutorRuntimeResult`

所以如果把下面这些字段也塞进 `ExecutorStepOutput`：

- `sample_id`
- `trajectory_id`
- `round_idx`
- `step_idx`
- `step_id`

会产生两个问题：

1. 和 `PendingExecution` / `StepRecord` 形成重复来源
2. executor parser 本来只负责解析模型文本，却被迫承担 orchestrator 状态拼装职责

因此目前更合理的理解是：

> `ExecutorStepOutput` 是“模型输出层对象”，不是“step 持久化记录对象”。

### 5.2 它和 `StepRecord` / `ExecutorRuntimeResult` 的边界

建议固定按三层理解：

1. `ExecutorStepOutput`
   - 解析 executor 模型原始返回后的内存对象
   - 关注 `cot` 和 `code`
   - 不负责描述 step 全量上下文
2. `StepRecord`
   - trajectory 里的步骤登记对象
   - 负责保存 `step_id`、`step_idx`、planner 对应关系、文件路径、消息 ID
   - 它是“这一步已经被系统登记了”的记录
3. `ExecutorRuntimeResult`
   - runtime 对 `executor_code.py` 的真实执行结果
   - 负责保存工具调用观测、输出图、文本、meta、stdout/stderr、error
   - 它是“这一步执行后观察到了什么”的记录

一句话说：

> `ExecutorStepOutput` 解决“模型说要执行什么”，`StepRecord` 解决“系统把这一步登记成什么”，`ExecutorRuntimeResult` 解决“这一步真实执行出了什么”。

### 5.3 现在要不要给 executor output 单独补 schema

当前已经补了一份最小：

- `offline_sft_pipeline/schemas/executor_step_output_schema.json`

但这里要强调，它的定位是：

- executor client 的内部结构化输出契约
- 不是和现有 5 份核心持久化 schema 完全同级的“第 6 份总表 schema”

这样做的原因是：

1. executor 这一侧确实需要一个稳定承接，方便模型按结构化格式输出
2. 但 executor 模型输出当前并不直接落成统一 JSON 总表，而是继续拆成：
   - `executor_cot.md`
   - `executor_code.py`
3. `step_id / step_idx / round_idx / sample_id / trajectory_id` 已经由 orchestrator 上下文和 trajectory schema 里的 `pendingExecution` / `stepRecord` 承接，不应在 executor 输出 schema 里重复

因此当前 schema 仍然只保持最小字段：

- `cot`
- `code`
- `raw_response_text`
- `metadata`

这样就能同时满足两件事：

1. executor 输出有明确结构化约束
2. 不把 executor output 和 step 持久化记录混成一个对象

### 5.4 为什么 `ExecutorStepOutput` 直接放在 `core/models.py` 目前是合理的

目前 `core/models.py` 的职责并不只是“5 份 schema 的 Python 映射”，它已经同时承担：

- schema-backed 顶层对象
- store / orchestrator 需要的内部数据对象
- 路径和状态关联对象

在这个阶段把 `ExecutorStepOutput` 放在这里，优点是：

1. executor client、store、orchestrator 以后都可以从同一个地方 import
2. 它和 `PendingExecution` / `StepRecord` / `ExecutorRuntimeResult` 本来就属于同一条 step 链
3. 当前文件规模还没大到必须拆分

后面如果 client 层真的长起来了，再考虑拆成：

- `core/models.py` 或 `core/state_models.py`
- `clients/contracts.py`

但现在先不拆更稳。

现在最顺的下一步是：

1. 实现 `ExecutorStepOutput` 对应的 parser
2. 实现 `planner_client.py`

  - fake 数据

而不是先写一套 fake client，后面再推倒重来。
