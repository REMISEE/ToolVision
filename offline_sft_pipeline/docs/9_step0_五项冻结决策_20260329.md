# 9 Step 0 五项冻结决策

日期：2026-03-29  
状态：v0.1 冻结稿  
目的：冻结 `core/store/orchestrator/exporter` 开工前必须确定的 5 个协议点，减少后续返工。

---

## 1. 一句话结论

v0.1 先按下面 5 条固定：

1. `question_id` 不是 `trajectory_id`
2. `sample_id` 用带数据集命名空间的稳定 ID
3. `trajectory_id` 用“样本 ID + 分叉路径”命名
4. `messages.json` 是“单条 trajectory 的滚动消息账本”
5. step 多图全部保存，但只有第一张图作为默认主输出图

---

## 2. 冻结项 1：ID 规则

### 2.1 先区分 3 个 ID

这 3 个 ID 不应该混用：

- `question_id`
  - 原始数据集里的样本题号
- `sample_id`
  - offline pipeline 的入口样本 ID
- `trajectory_id`
  - 某一条具体分叉轨迹的 ID

因此：

- 不能直接把原始 `question_id` 当 `trajectory_id`
- 因为同一个 sample 下面可能有多条 trajectory
- 也不能只用裸 `question_id`
  - 不同数据集之间可能重复

### 2.2 `sample_id` 规则

v0.1 固定为：

```text
<dataset_name>__<split>__<question_id>
```

例如：

- `textvqa__train__000001`
- `chartqa__val__128`
- `docvqa__test__abc123`

如果某个来源没有明确 `split`，则允许：

```text
<dataset_name>__<question_id>
```

说明：

- 这里推荐用 `__`，不推荐普通 `-`
- 因为原始 question id 里本身可能带 `-`
- `__` 更容易稳定切分

### 2.3 `trajectory_id` 规则

root trajectory：

```text
traj__<sample_id>__root
```

child trajectory：

```text
<parent_trajectory_id>__r<planner_round_idx:03d>_<suggestion_id>
```

例子：

```text
traj__textvqa__train__000001__root
traj__textvqa__train__000001__root__r000_s1
traj__textvqa__train__000001__root__r000_s1__r001_s2
```

这样做的好处是：

- 同一个 sample 下天然唯一
- 一眼能看出分叉路径
- 不需要额外查 parent 才知道它从哪条支路来

v0.1 先不做 hash 型短 ID。

## 3. 冻结项 2：落盘目录布局

这里说的“目录布局”，就是落盘的具体格式。

v0.1 建议固定成下面这样：

```text
offline_sft_pipeline/outputs/runs/<run_id>/
  samples/
    <sample_id>/
      root_sample.json
      artifacts/
        img_root_0.png
        img_root_1.png
      trajectories/
        <trajectory_id>/
          trajectory.json
          messages.json
          planner/
            round_000.json
            round_001.json
          steps/
            step_001/
              executor_cot.md
              executor_code.py
              runtime_result.json
              stdout.txt
              stderr.txt
              output_0.png
              output_1.png
            step_002/
              ...
          judge/
            step_001_cheap_filter.json
            step_002_cheap_filter.json
            trajectory_final_select.json
          exports/
            canonical_sft_sample.json
```

### 3.1 sample 级

sample 级目录只放所有 trajectory 共享的东西：

- `root_sample.json`
- root 原始图 artifacts
- 该 sample 下的所有 trajectories

### 3.2 trajectory 级

trajectory 级目录放这条分叉自己的全部执行历史：

- `trajectory.json`
- `messages.json`
- planner 历史
- steps 历史
- judge 历史
- export 结果

### 3.3 为什么这样分层

原因很简单：

- root 图是多个 child trajectory 共享的
- `messages.json` 和 `trajectory.json` 是每条 trajectory 独立演化的
- step 输出图也只属于某条 trajectory 的某一步

所以：

- root artifacts 放 sample 级
- step artifacts 放 trajectory 级

## 4. 冻结项 3：`messages.json` 的角色

### 4.1 它是什么

`messages.json` 是：

> 单条 trajectory 的滚动消息账本。

它既是：

- planner / executor prompt builder 的输入
- exporter 的直接来源之一

但它不是：

- runtime wrapper 的直接产物
- judge 的直接产物

### 4.2 谁创建、谁更新

创建方：

- `store.init_root_trajectory(...)`

更新方：

- orchestrator / store

不负责写它的模块：

- runtime wrapper
- judge

也就是说：

1. root sample 初始化时，先生成初始 `messages.json`
2. planner 输出单独写 `planner/round_xxx.json`
3. executor + runtime 执行完一步后，由 orchestrator 把这一步线性化追加进 `messages.json`
4. judge 只写 judge record，不写 messages

### 4.3 初始内容

root trajectory 初始化后，`messages.json` 至少有两条：

1. `system`
2. `user`

例如：

```json
[
  {
    "message_id": "m_sys",
    "role": "system",
    "content": "You are a helpful vision tool-use assistant.",
    "image_artifact_ids": [],
    "metadata": {
      "message_kind": "system_instruction"
    }
  },
  {
    "message_id": "m_user",
    "role": "user",
    "content": "价格标签上写的数字是多少？",
    "image_artifact_ids": ["img_root_0"],
    "metadata": {
      "message_kind": "user_question"
    }
  }
]
```

### 4.4 每执行一步后追加什么

每个已执行 step 追加两条：

1. `assistant`
2. `tool`

其中：

- `assistant` 记录这一 step 的局部 thought 和代码
- `tool` 记录 runtime 的文字返回和图像 artifact

例子：

```json
{
  "message_id": "m_step_001_assistant",
  "role": "assistant",
  "content": "<think>先裁出价格标签区域，再 OCR。</think>\n<tool_call name=\"code_image_tool\">...</tool_call>",
  "image_artifact_ids": [],
  "metadata": {
    "message_kind": "executor_step",
    "step_idx": 1,
    "planner_round_idx": 0,
    "suggestion_id": "s1",
    "step_id": "step_a",
    "executor_code_path": "steps/step_001/executor_code.py"
  }
}
```

```json
{
  "message_id": "m_step_001_tool",
  "role": "tool",
  "content": "18",
  "image_artifact_ids": ["img_step_001_0"],
  "metadata": {
    "message_kind": "tool_result",
    "step_idx": 1,
    "tool_name": "code_image_tool",
    "runtime_result_path": "steps/step_001/runtime_result.json"
  }
}
```

### 4.5 planner 输出要不要写进 `messages.json`

v0.1 先不要。

planner 输出保留在：

- `planner/round_xxx.json`

不追加进 `messages.json`。

原因：

- planner proposal 是分叉提案，不是已执行历史
- 只有真正执行过的 step 才应该进入 trajectory 的消息账本

## 5. 冻结项 4：同步 judge 的最小字段和 stop 规则

### 5.1 “最小字段”是什么意思

这里不是说 schema 只保留几个字段。

而是说：

> 在 hot path 里，orchestrator 真正依赖哪些 judge 字段做继续/停止决策，要先固定。

v0.1 目前 judge 不复杂，主要就是打分，所以同步控制层先收成一类记录即可：

- 每执行一步，产出一条 `judge_stage = "cheap_filter"` 的 step 级 judge record

### 5.2 这些字段怎么来

先区分两类字段：

#### A. orchestrator / policy 本地填写

这些不是 judge 模型“判断出来”的，而是系统上下文或控制层自己写的：

- `scope_type = "step"`
- `scope_step_idx`
- `judge_stage = "cheap_filter"`
- `keep_for_frontier`
- `exportable`
- `created_at`

其中：

- `keep_for_frontier` 不是必须由模型直接输出
- 更推荐由本地 policy 根据分数阈值和预算规则派生

#### B. judge 模型返回或从返回中解析

v0.1 现在先只要求一项真实打分：

- `overall_score`

以及一条简短说明：

- `note`

如果 judge 模型本身不产出解释，`note` 也可以由本地 policy 写，例如：

- `overall_score=0.18 < 0.25, prune`
- `overall_score=0.61, keep_for_frontier=true`

### 5.3 当前 v0.1 真正依赖的字段

如果你们现在的 judge 形态是“judge model 集群返回一个总分”，那么 hot path 里真正依赖的字段应当收缩为：

- `scope_step_idx`
- `judge_stage`
- `overall_score`
- `keep_for_frontier`
- `note`
- `exportable`

其他字段先全部降级为占位字段：

- `answerability_score = null`
- `tool_use_quality_score = null`
- `trajectory_progress_score = null`

也就是说：

- 当前真的做控制的是一个总分
- `keep_for_frontier` 由本地规则从总分导出
- 其他细分分数先不启用

### 5.4 推荐 stop 规则

v0.1 推荐先用这套简单规则：

1. runtime 执行失败
   - trajectory -> `failed`
2. executor 代码为空，或 runtime 成功但既没有输出图也没有有效文本
   - trajectory -> `pruned`
3. `overall_score < 0.25`
   - trajectory -> `pruned`
4. 相比上一步，`delta_score <= -0.20`
   - trajectory -> `stopped_early`
5. 连续两步 `abs(delta_score) < 0.03`
   - trajectory -> `stopped_early`
6. 预算耗尽
   - trajectory -> `max_step_reached`
7. 其余情况
   - `keep_for_frontier = true`

### 5.5 这些字段是否已经在 schema 里

是的，这些字段已经在现有 schema 里：

- `offline_sft_pipeline/schemas/judge_record_schema.json`

其中当前状态是：

- `overall_score` 是必填，且必须是 `0~1` 数字
- `answerability_score` / `tool_use_quality_score` / `trajectory_progress_score` 允许 `null`
- `keep_for_frontier` / `exportable` / `note` 是必填

所以按你现在的方案，完全可以：

- 只让 judge cluster 返回一个 `overall_score`
- 由本地 policy 决定 `keep_for_frontier`
- 其余细分分数全部写 `null`

这样能和当前 schema 兼容，不需要现在就引入 weak-model / committee summary。

## 6. 冻结项 5：step 主输出图语义

### 6.1 基本规则

runtime 返回多张图时：

- 所有图都保存
- 保留原始顺序
- `runtime_result.images[0]` 视为主输出图

也就是说：

- `output_0.png` 是默认主图
- `output_1.png`、`output_2.png` 是辅助图

### 6.2 为什么用第一张做主图

原因是：

- 当前 schema 没有单独的 `primary_image` 字段
- 但 orchestrator / judge / exporter 经常需要“当这一步只有一张代表图时，用哪张”
- 用 `images[0]` 作为统一规则最简单、最稳定

### 6.3 `messages.json` 怎么写多图

tool message 要保留全部返回图：

```json
{
  "role": "tool",
  "content": "...",
  "image_artifact_ids": [
    "img_step_003_0",
    "img_step_003_1",
    "img_step_003_2"
  ],
  "metadata": {
    "primary_image_artifact_id": "img_step_003_0"
  }
}
```

### 6.4 下一轮默认带哪些图

v0.1 默认只把下面这些作为下一轮 prompt builder / executor 的“主可见图”：

1. root images
2. 最新一步的主输出图

辅助图：

- 保留在 artifact 和 tool message 里
- 不默认自动继续带进下一轮

这样做是为了避免：

- 多图少见场景把上下文快速撑爆
- executor 在下一步默认面对过多图片

如果后面确实出现强依赖多 crop 并行观察的任务，再单独放宽。

## 8. 一句话版本

Step 0 冻结后，v0.1 的最小工程假设就是：

> `sample_id` 解决跨数据集唯一性，`trajectory_id` 解决分叉唯一性；`messages.json` 只记录单条 trajectory 的已执行消息历史；同步 judge 先只做一层简单打分控制；多图全部保存但默认只拿第一张当主输出图。
